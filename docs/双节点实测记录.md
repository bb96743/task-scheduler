# 双节点不重复执行 · 实测记录

> 实测时间：2026-11-17 17:04–17:09（本轮）
> 环境：Windows 11 · JDK 21.0.12 · Spring Boot 3.5.14
> 存储：H2 文件库 + `AUTO_SERVER=TRUE`（两个 JVM 进程共享同一份数据文件）

## 一、部署方式

```bash
# 节点 A（首次启动负责建表灌数据）
java -jar target/task-scheduler-1.0.0.jar --spring.profiles.active=nodes \
  --server.port=8081 --scheduler.node-id=node-a --scheduler.scan-interval-ms=1000

# 节点 B（同一数据库，跳过 schema 初始化避免互相清表）
java -jar target/task-scheduler-1.0.0.jar --spring.profiles.active=nodes \
  --server.port=8082 --scheduler.node-id=node-b --scheduler.scan-interval-ms=1000 \
  --spring.sql.init.mode=never
```

两个节点连**同一个数据库**，`scheduler.node-id` 分别取 `node-a` / `node-b`，扫描间隔均为 1 秒。
H2 的 `AUTO_SERVER=TRUE` 让第二个进程以自动服务器模式接入同一文件，等价于生产环境两台机器连同一个 MySQL。

## 二、节点心跳

`GET http://localhost:8081/api/nodes`：

| nodeId | status | 说明 |
|--------|--------|------|
| node-a | ONLINE | 心跳正常续约 |
| node-b | ONLINE | 心跳正常续约 |
| node-1 | OFFLINE | 初始种子节点，30s 未续约后被自动摘除 |

第三行验证了**宕机识别**：超过 `node-timeout-ms`（默认 30s）未续约的节点会被置为 OFFLINE。

## 三、实测一：常规负载下两节点各干一半

双节点共同运行 55 秒（5 个演示任务，其中 4 个启用），执行记录汇总：

```
节点 A 视角：任务 5 个，执行记录 18 条
节点 B 视角：任务 5 个，执行记录 18 条
重复 fireTime 数：0

按节点分布：{'node-a': 9, 'node-b': 9}

任务                  执行数   节点分布                 状态分布
demo-fail-task        6      {'node-a': 3, 'node-b': 3}  {'FAILED': 6}
demo-flaky-task       5      {'node-b': 4, 'node-a': 1}  {'FAILED': 4, 'SUCCESS': 1}
demo-shard-task       4      {'node-a': 3, 'node-b': 1}  {'SUCCESS': 4}
demo-success-task     3      {'node-a': 2, 'node-b': 1}  {'SUCCESS': 3}
```

**关键结论**：

1. 18 条执行记录中 **重复 fireTime 为 0**，同一触发时刻只落库一次
2. 执行均匀分在两个节点（9 : 9），证明两个节点都在真实抢触发权，不是单节点空跑
3. 两个进程读到完全相同的 18 条记录，说明它们确实共用同一个库
4. 若没有互斥，18 条会变成 36 条

## 四、实测二：每秒触发的高频竞争压测

常规任务每 30–45 秒才到期一次，两节点真正“撞车”的窗口很窄。为了把竞争压到极限，额外注册一个 **每秒触发** 的任务：

```bash
curl -X POST http://localhost:8081/api/tasks -H 'Content-Type: application/json' -d '{
  "taskName":"race-task","taskGroup":"RACE","cronExpression":"0/1 * * * * ?",
  "handlerName":"demoSuccessHandler","shardTotal":1,"retryMax":0,"retryInterval":1
}'
```

两个节点扫描间隔 1 秒、任务每秒到期，**每一秒两个节点都会同时看到同一条到期任务**。运行 46 秒的结果：

```
race-task 执行记录：46 条
时间跨度：17:07:53 → 17:08:38（46 秒）
重复 fireTime：0 个
节点分布：{'node-a': 29, 'node-b': 17}
状态分布：{'SUCCESS': 45, 'RUNNING': 1}（最后一条正在跑）
```

46 秒恰好 46 条，一秒一条，不多不少。这是最强的一组证据：**竞争最激烈时也没有出现两条记录**。
若唯一约束失效，46 秒会产生约 90 条记录。

## 五、实现依据

```
sched_task_fire 的唯一约束 uk_task_fire(task_id, fire_time)
  ├─ 节点 A INSERT 成功       → 获得本次执行权，继续建执行记录
  └─ 节点 B INSERT 冲突        → DuplicateKeyException，直接 return 跳过

sched_task_execution 的唯一约束 uk_exec_task_fire(task_id, fire_time)
  └─ 第二道保险：即使触发记录异常，也不会产生两条执行记录
```

约束建在数据库层，不依赖应用内锁、Redis 或 ZK，因此跨进程、跨机器、跨语言均有效。

**关于日志**：赢家在毫秒级完成「插 fire 记录 → 推进 next_fire_time → 建执行记录」并提交，
输家 1 秒后的下一轮扫描读到的已经是推进后的 `next_fire_time`，因此正常路径下大多根本走不到冲突分支；
真撞上时走的是 `DuplicateKeyException` 分支，日志级别为 DEBUG。
换句话说，唯一约束在这里是**兜底安全网**，而快速提交让绝大多数竞争在业务层就被自然化解。

节点侧能看到的正常日志（node-a 启动初期真实输出）：

```
节点 node-a 触发任务 [demo-success-task]，执行实例 1
节点 node-a 触发任务 [demo-fail-task]，执行实例 2
节点 node-a 触发任务 [demo-shard-task]，执行实例 3
```

两节点日志中不存在「同一任务同一秒触发两次」，与执行记录一致。

## 六、复现命令

```bash
# 1. 起两个节点（见上）
# 2. 拉取某任务的执行记录，统计重复 fireTime
curl -s http://localhost:8081/api/tasks/1/executions | python -c "
import sys,json,collections
d=json.load(sys.stdin)['data']
c=collections.Counter((e['taskId'], e['fireTime']) for e in d)
print('总执行数:', len(d))
print('重复 fireTime 数:', sum(1 for v in c.values() if v > 1))
print('按节点分布:', collections.Counter(e.get('nodeId') for e in d))
"
```

生产环境只需把 `spring.datasource.url` 指向同一 MySQL 实例，其余逻辑不变。
