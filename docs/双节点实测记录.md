# 双节点不重复执行 · 实测记录

> 实测时间：2026-11-17 16:27–16:30
> 环境：Windows 11 · JDK 21.0.12 · Spring Boot 3.5.14
> 存储：H2 文件库 + `AUTO_SERVER=TRUE`（多进程共享同一库）

## 一、部署方式

```bash
# 节点 A
java -jar target/task-scheduler-1.0.0.jar --spring.profiles.active=nodes \
  --server.port=8081 --scheduler.node-id=node-a

# 节点 B（同一数据库，跳过 schema 初始化避免互相清表）
java -jar target/task-scheduler-1.0.0.jar --spring.profiles.active=nodes \
  --server.port=8082 --scheduler.node-id=node-b --spring.sql.init.mode=never
```

两个节点使用**同一个数据库文件**，`scheduler.node-id` 分别为 `node-a` / `node-b`，调度扫描间隔均为 1 秒。

## 二、节点心跳

`GET http://localhost:8081/api/nodes`：

| nodeId | status | 说明 |
|--------|--------|------|
| node-a | ONLINE | 心跳正常续约 |
| node-b | ONLINE | 心跳正常续约 |
| node-1 | OFFLINE | 初始种子节点，超时后被自动标记离线 |

第三行验证了**宕机识别**：超过 `node-timeout-ms`（30s）未续约的节点会被置为 OFFLINE。

## 三、不重复执行验证

查询 `demo-success-task`（每 30 秒触发一次）在双节点共同调度期间的执行记录：

`GET http://localhost:8081/api/tasks/1/executions`

```
总执行数: 3
重复 fireTime 数: 0
按节点分布: {'node-b': 1, 'node-a': 2}

2026-11-17T16:28:00  node-b  SUCCESS
2026-11-17T16:27:30  node-a  SUCCESS
2026-11-17T16:27:25  node-a  SUCCESS
```

**关键结论**：

1. 同一 `fireTime` 只出现一次，**重复数为 0**
2. 执行分散在两个节点（node-a 2 次、node-b 1 次），说明两个节点都在参与抢触发权
3. 若不加锁，3 个触发时刻会产生 6 条执行记录；实际只有 3 条

## 四、实现依据

```
sched_task_fire 的唯一约束 uk_task_fire(task_id, fire_time)
  ├─ 节点 A INSERT 成功 → 获得执行权
  └─ 节点 B INSERT 冲突（DuplicateKeyException）→ 跳过本次触发

sched_task_execution 的唯一约束 uk_exec_task_fire(task_id, fire_time)
  └─ 作为第二道保险，即使触发记录异常也不会产生重复执行
```

约束建在数据库层，不依赖应用内锁或 Redis，因此跨进程、跨机器均有效。

## 六、复现命令

```bash
curl -s http://localhost:8081/api/tasks/1/executions
# 统计重复 fireTime
curl -s http://localhost:8081/api/tasks/1/executions \
  | python -c "import sys,json,collections;d=json.load(sys.stdin)['data'];\
c=collections.Counter(e['fireTime'] for e in d);\
print('重复 fireTime 数:', sum(1 for v in c.values() if v>1))"
```

生产环境只需把 `spring.datasource.url` 指向同一 MySQL 实例，其余逻辑不变。
